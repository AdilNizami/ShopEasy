# ShopEasy final architecture review

## Scope and method

This is a repository-level review of the current contracts, service boundaries,
integration code, gateway, authentication, frontend calls, tests, and container
configuration. Concrete defects found during review were fixed and regression
tests were added. “No issue found” means the code was inspected for the named
concern; it does not mean a full production deployment has been verified.

## Remaining risks

- **No runtime verification:** Python, Docker, and frontend dependencies are unavailable in this environment. The Python suite, Ruff, frontend build, JSON Schema meta-validation, and Compose image/startup checks should be run in CI or a configured developer environment before merge/deployment.
- **Shared JWT signing key:** Auth, Gateway, Orders, Payments, and Catalog validate HS256 tokens using the same secret. Any compromised verifier can mint tokens. For production, prefer asymmetric signing so verifiers receive only a public key, with rotation and key IDs.
- **Browser token storage:** The frontend holds access tokens in browser storage, which increases impact of script injection. Add a reviewed CSP and consider a same-site, secure, HttpOnly BFF cookie design before production.
- **Development Compose defaults:** Local fallback passwords are not production secrets. Use a deployment secret manager, separate least-privilege credentials, TLS, and a deployment-specific Compose/Kubernetes configuration.
- **Migrations:** Startup schema upgrades are idempotent DDL helpers rather than a complete versioned migration framework. Production roll-forward/rollback and multi-instance migration coordination need a migration tool and procedure.
- **Operational DLQ lifecycle:** The dashboard exposes failed messages, but there is no controlled replay command, retention/expiry policy, or alert threshold. Define these before operating real traffic.
- **Outbox operational policy:** Retries are bounded per delay but the row remains pending indefinitely; persistent schema/configuration failures can grow the table. Add age/volume alerts and an operator repair process.
- **Checkout saga reconciliation:** A timeout may leave reservation/payment outcome uncertain. Idempotency and local compensation are present, but late payments, cancellation/refund policy, expiry, and reconciliation require a real provider and explicit business decisions.
- **External shipping producer:** `OrderShipped` and `OrderDelivered` are consumed, but this repository has no Shipping context that publishes them. They are integration contracts for a future/external producer.
- **Observability access:** Engineering endpoints are operator-protected, but production should additionally restrict network access and audit access to operational data.
- **Testing breadth:** There is no live RabbitMQ/PostgreSQL integration environment or browser E2E coverage verified here. Add CI services and end-to-end flows for broker topology, transaction semantics, and checkout UI/API compatibility.

## Fellowship concepts demonstrated

- **API-first and contract-first:** `/v1` endpoints and versioned event JSON Schemas are published independently of implementation details.
- **Bounded contexts and ownership:** Catalog, Orders, Payments, and Inventory own their rules and persistence boundaries; shared code is limited to technical concerns.
- **ASK vs TELL:** HTTP is used when checkout needs an answer now; past-tense events announce committed facts for asynchronous reactions.
- **Queues and asynchronous integration:** RabbitMQ consumers do not need publisher database access, and publishers do not synchronously call event consumers.
- **Plan for failure:** explicit timeouts, retry classification, bounded delays, DLQ routing, circuit breaking, idempotent inboxes, and correlation IDs make failure behavior visible and controlled.
- **Transactional Outbox:** business state and event intent commit together. Confirmed publishing reduces loss risk while stable event IDs and consumer deduplication handle unavoidable duplicate delivery.
- **Versioning and compatibility:** `/v1` and event v1 schemas remain stable; additive changes are distinguished from breaking major-version changes.
- **Gateway as one front door:** the frontend uses a routing/authentication/observability entry point while domain rules stay in their owning services.
